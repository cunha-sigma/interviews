# Project Context Brief: ML Engineer Interviewing (Traffic Shaping / Universal Ads)

## 1. Project purpose

This folder is a self-contained interview-operations kit for hiring a Senior/Principal ML Engineer onto the Traffic Shaping team at Universal Ads (a video ad platform for TV monetization, staffed via Sigma Software). It contains the source job requisition, an elaborated interviewer playbook (question bank, live design-challenge script, scorecard, and decision rules), the raw Portuguese interview-structure outline that playbook was built from, a candidate-feedback template, and CVs for two candidates currently in the pipeline. The intent is that any interviewer (or a future Claude Code session) can pick up this folder and run a consistent, well-calibrated interview without prior context.

## 2. The role being hired for

`role_description.md` is the formal, somewhat generic-feeling job description: Senior/Principal ML Engineer, São Paulo/remote, for "Our Client" — a video ad platform for TV monetization handling billions of daily requests and terabytes of data, on the "Ad Intelligence and Forecasting" team. It emphasizes Scala/Spark model implementation, Kafka, AWS deployment, 5-8 years of Big Data/ML experience, technical leadership, mentoring, full feature-lifecycle ownership, and SDLC/Agile fluency. Nice-to-haves: Golang, ad-industry experience. The doc has rough edges (typos like "larges system," a repeated mentoring bullet) and never mentions "traffic shaping" or "decision service."

`interview_plan.md` explicitly overrides this framing: the interviewer (Rodrigo Cunha, Principal ML Engineer) notes that day-to-day work is actually building and operating systems like the traffic-shaping architecture that motivates this whole interview project — not generic Scala/Spark/Kafka/AWS work. Practically, this means the interview should screen for low-latency real-time decisioning, MLOps around model serving, and distributed-systems/production ownership rather than the specific tech stack listed in the JD. Candidates should be evaluated against this real job, not the literal requisition text.

## 3. Interview format & timeline

`interview_structure.md` (Portuguese, ~6 lines) is the original source outline, later translated and elaborated into `interview_plan.md`. It specifies a 5-segment structure with no rubric or question content of its own:

1. **10 min** — candidate self-introduction ("contar sua história")
2. **10 min** — interviewer explains context, challenges, and expectations
3. **10-20 min** — technical questions (unlabeled in the source; fully detailed only in interview_plan.md)
4. **10-20 min** — live problem: system design for a service that delivers a classification decision under a real-time API with P99 < 10ms latency
5. **5 min** — candidate questions

`interview_plan.md` adopts this exact timeline and fleshes out segments 3 and 4 into a full technical evaluation.

## 4. Technical evaluation content

**Segment 3 — Q&A bank** (organized into screening areas, each with an answer key):
- **SWE fundamentals / Big-O** (reading code, not necessarily live coding): three snippets — (A) nested-loop duplicate detection, O(n²)→O(n) via set; (B) rolling-average slicing, O(nk)→O(n) via running sum; (C) a recursive "combined_risk" fib-like function — tests whether the candidate distinguishes time (Θ(φⁿ)/O(2ⁿ)) from space (O(n), not O(2ⁿ), due to call-stack depth) rather than reflexively saying "recursion = exponential everything"; expects memoization/iterative-DP fixes.
- **ML fundamentals**: bias/variance, metric choice under class imbalance (AUC-PR), time-based vs. random train/test splits (leakage), recall vs. ROI-driven thresholding, drift detection without real-time ground-truth labels.
- **MLOps/DevOps**: what must be versioned as a single unit (encoder + classifier + threshold), progressive deployment strategy (shadow → A/B → canary → promote), deterministic hashing on a stable ID for A/B splits, risks of a training pipeline reading directly from a production transactional DB.
- **K8s/Docker/serving**: liveness vs. readiness probes, KEDA vs. HPA, gRPC vs. REST inside a 10ms budget, what NVIDIA Triton solves that Flask/FastAPI doesn't (batching, multi-backend, ensembles), how to prove a P99<10ms SLA (k6/ghz/locust, percentiles not averages), pod-death behavior.
- **Math**: precision/recall formulas and optimization scenarios, what calibration means and why it matters for thresholding, why P99 (not average) matters given non-normal latency distributions, optional GBT vs. single-tree math.
- **Ownership**: an example of owning a system end-to-end with an unprompted decision; when to decide vs. escalate.

**Segment 4 — live system-design challenge**: AdTech scenario — bid requests flow through real-time auctions, System A → ML filter → System B, and the filter's decision must return within P99<10ms at millions of requests/sec; an ML failure must never block or take down auction traffic. The candidate designs end-to-end from data to decision to production serving.

Deliberate design choice: the interviewer must never say "classifier," "score," or "threshold" — if asked directly how the decision is made, the interviewer turns the question back on the candidate. This tests whether the candidate independently arrives at "continuous score + configurable threshold" as the mechanism and can articulate alternatives (fixed rules, global cutoff, per-segment cutoffs, cost-sensitive/ROI decisioning, bandits).

**Facilitation tracking table** — 9 topics scored U (unprompted) / P (prompted) / M (missing), each with a suggested nudge: (1) feature/data pipeline & training-serving skew, (2) decision mechanism, (3) per-segment vs. global threshold, (4) how the threshold value is chosen, (5) low-latency serving stack (compiled runtime, optimized inference server, in-memory feature lookup), (6) graceful degradation/fallback, (7) deployment safety for new model versions, (8) monitoring/drift, (9) scaling strategy.

**Bar levels**:
- **Above bar** — independently proposes score + configurable threshold, reasons explicitly about 10ms budget allocation across the pipeline, raises graceful degradation unprompted.
- **At bar** — arrives at a workable pipeline shape but needs 1-2 nudges.
- **Below bar** — treats the problem as offline ML (accuracy, cross-validation) and ignores systems/latency/production-safety concerns even after nudges.

Segment 5 (candidate questions) is also scored qualitatively: note whether questions skew toward technical depth vs. logistics/compensation.

## 5. Scorecard & decision guidance

Scoring is 1-4 per dimension, with weighted rows:
- **High weight**: SWE fundamentals/Big-O, ML fundamentals, MLOps/DevOps, K8s/serving infra, low-latency/performance instincts, system-design synthesis.
- **Medium weight**: math foundations, ownership/self-management, communication.

Rationale given: the High-weight rows (SWE fundamentals, low-latency instincts, system-design synthesis especially) are the hardest to coach on the job and therefore gate the decision, whereas ML-fundamentals gaps are considered more coachable since the hiring manager (Rodrigo) is already the ML lead.

**Decision guidance**:
- **Strong hire** — above-bar or at-bar on all High-weight rows, with no "Missing" marks on threshold-choice, degradation, or latency-budget topics.
- **Borderline** — at-bar on most High rows but needing 1-2 nudges throughout, OR a single sharp category gap (e.g., strong SWE but weak ML, or vice versa) → recommend a targeted second round (e.g., a live k6/ghz load-test exercise).
- **No hire** — below-bar on SWE/Big-O, or the candidate frames Segment 4 as a pure offline-ML problem even after nudging.

A specific follow-up suggestion is included: if low-latency serving signal is thin, run a second-round exercise where the candidate containerizes a toy model behind gRPC and load-tests it with k6/ghz to find the P99 breaking point.

## 6. Candidate review process

`candidates/review_template.md` is a 36-line template to be filled out after each interview, using a uniform 1-5 star rating plus free-text feedback per section, across 5 sections:
1. **Overall rating** — holistic feedback on the whole interview.
2. **English level** — fluency, vocabulary, grammar, business register.
3. **Interpersonal skills** — one overall grade covering receptiveness to feedback, collaboration, attitude to work, and communication, with per-skill comments.
4. **Analytical skills** — one overall grade covering ability to collect/analyze information, problem-solving, and decision-making, with per-skill comments.
5. **Candidate's level** — placement on a seniority ladder (Intern/Junior/Middle/Senior/Principal) with written justification.

Notably, there is no explicit hire/no-hire recommendation field and no signature/date field in this template — it captures assessment but not a final decision.
